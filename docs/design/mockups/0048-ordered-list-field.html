#698 · ADR-0048 §6 · mockup — tried, not sketched

The list field: a named group, kept nested

One new type. An item is either an existing named field group — the same MetadataGroupDefinition that flattening applications use today, consumed nested instead — or a single value (sugar for a one-member shape). "Group" stays the only shape noun; there is no "record". One row widget everywhere, one density rule (B2). Fixture: a character's Open questions (group members: question · status · note).

A · Defining one (type editor)

SchemaFieldInlineEditor + one new config block

The type picker gains List. Its whole config is one question — what is an item? — answered with a named group or a single value type. A multi-field shape is always a group (defined once, in Groups, never re-declared per list); a single-value list skips the ceremony. The Default row uses the exact widget from section B (the #40 rule); it is collapsed here because defaults for lists are rare.

B · Editing one (metadata rail)

live — drag rows, click to expand, add, remove

Collapsed row = title member (the group's first text-ish member) + status pill + muted note snippet. Click expands in place, one row at a time — the schema-field-row idiom, accent-striped. The header stays put while open (title and pill track your typing); click it again, or any other row, to collapse. No Done button — values land as you type, the same autosave contract as every other rail field. Member fields reuse the per-scalar widgets verbatim (FieldValueEditor per member). Order is the value; the drag handle is the only reorder affordance.

B2 · The same widget, thinner shapes

live — one density rule, derived from the item shape

Not every list is a group. The rule: one member of an inline-editable type (text · number · select · color · boolean) → edit directly in the row — no expand step, no title/summary split; a plain list of strings must not cost three clicks per item. A single long_text member keeps the row-per-item frame with a growing textarea. Two or more members → section B's collapsed row + expand-in-place. Same widget, same grip/add/remove chrome — only the row's interior changes. A plot template's beat roster (name · guidance · act) lands in the section-B form with nothing new. long_text members use the app's default long_text editor (MetadataLongTextEditor, via the same FieldValueEditor dispatch as every member) — the plain textareas on this page are the static mockup's stand-in, not the proposal.

C · An AI proposal, per item

toggle "AI proposal arrives" above

The 0046 flip, at item grain instead of whole-value: edited rows (amber) flip current↔proposed on click; added rows arrive tinted green; removed rows are struck. Adopting follows compare.resolve's click-to-adopt — nothing is written until Done, same as lore today. Items are matched by position-with-content-similarity server-side; the UI only ever sees add/edit/remove.

Storage, proposed: item_type lists store a flat YAML scalar sequence (exactly how multi_select stores today); item_group lists store a sequence of maps keyed by member key. One internal model — the scalar form is normalized to a one-member shape before validation and the widget ever see it.

Deliberately unsettled here: the wire grammar for per-item AI patches (S2 ships whole-list validation; per-item flips can start as a diff computed client-side), and nested entity_ref/tags members — the healers only walk top-level values today, so v1 may exclude reference-typed members from item shapes rather than half-support them.
